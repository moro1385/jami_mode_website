# فاز ۶ — ثبت خطا و کندی و محافظ خطای رندر

این بسته محلی است و پس از انتشار هماهنگ Node/مرورگر قابل پذیرش زنده است. فعلاً متغیر جدید، سرویس خارجی، Migration، درخواست پرداخت یا فعال‌سازی گیت ندارد. بررسی شش متغیر لیارا و گیت‌های فاز۵ به درخواست مالک موکول مانده‌اند؛ گیت‌های دیتابیس طبق آخرین خواندن خاموش‌اند.

## ثبت HTTP در سرور

Middleware پیش از relay، parserها و routeها نصب می‌شود. فقط خانواده‌های ثابت API و خوراک ترب را مشاهده می‌کند؛ نام محصول، مسیر واقعی، query، شناسه سفارش/حساب، header، IP، بدنه و متن exception وارد رویداد نمی‌شود. شناسهٔ UUID تازه را سرور می‌سازد و در X-Request-ID برمی‌گرداند؛ شناسهٔ ارسالی مشتری مورد اعتماد نیست. در پاسخ کش‌شده ممکن است شناسه متعلق به درخواست اصلیِ تولیدکنندهٔ کش باشد.

رویداد http_request شامل requestId، family، method محدود، status، durationMs و outcome است. درخواست موفقِ کمتر از دو ثانیه لاگ ندارد. خطاهای ۴xx/۵xx، موفقِ کند و قطع پاسخ ثبت می‌شوند؛ status پاسخ قطع‌شده null است و موفقیت فرض نمی‌شود. این پایش وضعیت HTTP است؛ پاسخ ۲۰۰ به معنی تسویه مالی تأییدشده نیست.

حداکثر ۶۰ رویداد در دقیقه برای هر فرایند نوشته می‌شود. تعداد موارد کنارگذاشته‌شده با http_observation_suppressed در اولین رویداد پنجرهٔ بعد گزارش می‌شود؛ در نبود درخواست بعدی، این گزارش خودبه‌خود ارسال نمی‌شود. این سقف برای جلوگیری از رشد بی‌حد لاگ است، نه شمارندهٔ کامل خطا/درصد موفقیت. خطای log sink رفتار پاسخ API را تغییر نمی‌دهد. خروجی به console سرور می‌رود؛ جمع‌آوری، retention، جست‌وجو و هشدار بیرونی در لیارا هنوز نصب/تأیید نشده‌اند. زمان را سامانهٔ جمع‌آوری لاگ ثبت می‌کند؛ این ماژول timestamp مستقل اضافه نمی‌کند.

لاگ قبلی خوراک ترب که نام فیلدهای درخواست و message خطای provider را چاپ می‌کرد حذف شده؛ شکست همان مسیر توسط observer پوشش داده می‌شود. دیگر consoleهای قدیمی فرانت‌اند با این تغییر پاک‌سازی سراسری نشده‌اند.

## خطای رندر مرورگر

ApplicationErrorBoundary بالای App قرار گرفته است. خطای render/lifecycle فرزندان به صفحهٔ فارسی با بارگذاری مجدد تبدیل می‌شود؛ نام/متن exception در رابط نشان داده نمی‌شود و کد جدید تنها رویداد ثابت ui_render_failed را در کنسول محلی می‌نویسد. چیزی به سرویس بیرونی فرستاده نمی‌شود. React یا مرورگر ممکن است گزارش کنسول داخلی خودش را داشته باشد؛ این بسته تضمین پاک‌سازی تمام گزارش‌های داخلی کتابخانه‌ها را نمی‌دهد.

بارگذاری مجدد صرفاً reload صفحه است؛ سبد، نشست و داده‌های localStorage پاک نمی‌شوند و درخواست پرداخت دوباره خودکار انجام نمی‌شود. پیام به کاربر یادآوری می‌کند قبل از پرداخت دوباره، وضعیت سفارش را بررسی کند. خطای event handler، promise و قطعی شبکه باید در سرویس مربوط رسیدگی شود؛ ErrorBoundary آن‌ها را پوشش نمی‌دهد.

## پذیرش و کارهای باقی‌مانده

آزمون‌های Node روی HTTP محلی واقعی با پاسخ ساختگی، کنترل حریم خصوصی و شناسه، حذف لاگ موفق سریع، کندی، سقف ثبت، قطع پاسخ و شکست sink را پوشش می‌دهند. آزمون component پوشش fallback، عدم افشای متن خطا و حفظ وضعیت ذخیره‌شده را دارد.

پس از انتشار، بدون ساخت پرداخت/پیام/دادهٔ واقعی، یک مسیر API ناموجود باید ۴۰۴ با X-Request-ID بدهد و همان شناسه فقط در یک رویداد api_other دیده شود. سلامت live/maintenance باید رفتار قبلی را حفظ کند. ذخیره/بازیابی لاگ و تأخیر واقعی در محیط لیارا مستقل بررسی شود؛ مقدار token/header یا لینک امضاشده برای گزارش‌گیری کپی نشود.

باقی‌ماندهٔ تسک مانیتورینگ فاز۶: مقصد و retention لاگ، مانیتور مستقل دسترس‌پذیری، معیار و مقصد هشدارهای مالی، داشبورد عملیاتی و پذیرش میزبانی‌شده. هشدار ایمیل/پیامک/وبهوک بدون تعیین مقصد و مجوز ارسال ساخته نشده است. کل فاز۶ با این بسته Done نیست.


## ابزار بررسی سلامت، بدون ورود به لیارا

از پوشهٔ محلی پروژه اجرا کنید:

```sh
node scripts/check-site-health.mjs
```

در یک نوبت، سه GET محدود و هم‌زمان روی live، maintenance و Auth health مسیر واسط می‌فرستد. بدنهٔ پاسخ حداکثر ۳۲ KiB، مهلت هر بررسی ۱۰ ثانیه، بدون retry، Cookie، Authorization، رمز، redirect یا نوشتن است. فقط کلید عمومی فعلی برای Auth health لازم است؛ ابزار فایل env یا کلید خصوصی نمی‌خواند. origin فقط jamimode.ir/www با HTTPS یا loopback صریح روی پورت‌های توسعهٔ مجاز است.

خروجی JSON شامل نام ثابت بررسی، HTTP status، علت محدود و زمان پاسخ است؛ بدنهٔ دریافتی چاپ نمی‌شود. exit=0 یعنی هر سه بررسی پذیرفته شدند؛ exit=1 یعنی دست‌کم یکی ناموفق و exit=2 یعنی ورودی نامعتبر. result=degraded یعنی بخشی پاسخ معتبر دارند. reason=network_error با status=null فقط ناموفق‌بودن دسترسی همین اجرا را ثابت می‌کند؛ قطعی جهانی سایت یا علت فیلترینگ را اثبات نمی‌کند. health عمومی جای ورود واقعی، Storage، انبار، پرداخت یا تطبیق نسخهٔ هاست را نمی‌گیرد.

این ابزار یک‌بار اجرا می‌شود؛ هیچ cron، automation، اشتراک سرویس یا ارسال هشدار خودکار ساخته نشده است. تنظیم مانیتور مستقل و مقصد هشدار بعداً به دسترسی/تصمیم مالک نیاز دارد.

## خلاصهٔ امن لاگ صادرشده

فایل خروجی لاگ را بیرون repo نگه دارید و مسیر واقعی همان فایل را بدهید:

```sh
node scripts/summarize-observations.mjs --file "C:/path/outside-repository/app.log"
```

بدون --file از stdin می‌خواند. سقف ورودی ۸ MiB و صد هزار خط است؛ رکورد بیش از ۱۶۳۸۴ کاراکتر کنار گذاشته می‌شود. logهای prefixدار و JSONL/CRLF پذیرفته‌اند. تنها schemaهای ثابت http_request، suppression، maintenance_health و ui_render_failed پردازش می‌شوند؛ فیلد ناشناخته، family دلخواه، شناسه/عدد نامعتبر و status ناسازگار رد می‌شوند. خطوط خام، requestId، URL یا محتوا از فایل ورودی برگردانده یا کپی نمی‌شود. تنها تعدادها، خانوادهٔ ثابت و بیشینهٔ زمان مشاهده‌شده در خروجی‌اند. این شمارش جای dashboard با بازهٔ زمانی/مخرج درخواست‌ها نیست؛ uptime، نرخ موفقیت و تسویهٔ پرداخت از آن محاسبه نمی‌شوند.

incomplete=true یعنی رکورد کنارگذاشته‌شده/نامعتبر یا suppression وجود دارد؛ incomplete=false نیز تضمین کامل‌بودن export یا کل ترافیک نیست، چون درخواست‌های موفق سریع اصلاً log ندارند. exportهای تکراری/هم‌پوشان رویداد را دوباره می‌شمارند. ui_render_failed فقط در صورتی شمرده می‌شود که گزارش کنسول مرورگر عمداً در ورودی قرار داده شده باشد؛ جمع‌آوری خودکار مرورگر اضافه نشده است. تعداد transitionهای maintenance بیان وضعیت لحظه‌ای همهٔ سامانه نیست.

ابزار هیچ فایل، گیت یا سرویس را تغییر نمی‌دهد. ورودی غیرقابل‌خواندن/بیش‌ازحد با پیام کلی و exit=2 رد می‌شود و مسیر فایل یا exception چاپ نمی‌شود. فایل‌های واقعی لاگ را وارد Git یا چت نکنید؛ برای عیب‌یابی از خلاصه و کد وضعیت استفاده کنید. این ابزارها محلی‌اند و طبق .liaraignore همراه برنامه روی هاست قرار نمی‌گیرند.


## تاریخچهٔ محدود و تشخیص اختلال/بازیابی

ابزار record-site-health همچنان فقط با اجرای صریح یک نوبت بررسی می‌کند. این ابزار را از یک کامپیوتر/سرور پایش مستقل اجرا می‌کنند؛ وابستگی به خود process فروشگاه ندارد. در این بسته هیچ برنامهٔ دائمی یا زمان‌بندی واقعی نصب/اجرا نشده است. نمونهٔ CMD ویندوز برای استفادهٔ بعدی مالک:

```cmd
mkdir "%LOCALAPPDATA%\JamiMode-Monitoring"
node scripts/record-site-health.mjs --state-file "%LOCALAPPDATA%\JamiMode-Monitoring\jamimode-health-history.json"
```

فایل تاریخچه باید نام اختصاصی jamimode-health-history.json و مسیر مطلق با پوشهٔ از قبل موجود خارج repo داشته باشد. فایل موجود فقط با قالب اختصاصی نسخه۱ پذیرفته می‌شود؛ متن نامرتبط، symlink، hard link و فایل بیش از ۱ MiB رد می‌شوند. مسیر واقعی پوشه بررسی می‌شود تا alias داخل repo پذیرفته نشود. این محافظت عملیاتی برای فایل‌های ابزار است؛ تضمین در برابر مهاجم محلی هم‌سطح کاربر نیست.

حداکثر ۲۸۸ نمونهٔ آخر و ۴۰ رویداد آخر در یک snapshot نگهداری می‌شود؛ نمونهٔ قدیمی در snapshot جدید کنار می‌رود، نه اینکه فایل‌های دیگر پاک شوند. این سقف تعداد است، نه تضمین نگهداری چند روز. اطلاعات ذخیره‌شده همان وضعیت‌ها و زمان‌های محدود سه endpoint عمومی است؛ دادهٔ حساب/سفارش یا پاسخ خام ذخیره نمی‌شود. ابتدا فایل موقت اختصاصی نوشته و سپس rename می‌شود. قفل پوشه‌ای هم‌زمانی را رد می‌کند و قفل قدیمی خودکار ربوده/پاک نمی‌شود. در crash ممکن است lock/temp بماند؛ پیش از پاک‌سازی دستی فقط مسیر اختصاصی، مطمئن شوید هیچ writer فعال نیست. هیچ پاک‌سازی بازگشتی یا حذف فایل کاربر در ابزار وجود ندارد. mode پیشنهادی در ویندوز معادل ACL خصوصیِ تأییدشده نیست.

سه مشاهدهٔ ناموفق پیاپی برای هر probe یک monitor_problem می‌سازد؛ دو مشاهدهٔ موفق پیاپی بعد از اختلال یک monitor_recovered می‌سازد. شکست پراکنده streak را از نو شروع می‌کند؛ مشکل تکراری تا تغییر وضعیت هشدار تازه نمی‌سازد. تعداد مشاهده با دقیقه/مدت اختلال یکی نیست. state و streak در snapshot می‌مانند و restart آن را فراموش نمی‌کند. تغییر origin تاریخچه یا عقب‌رفتن ساعت پیش از نوشتن رد می‌شود.

خروجی شامل نتیجه و رویدادهای تازه است و تنها در فایل محلی/stdout می‌ماند؛ ارسال پیامک، ایمیل، webhook یا اعلان دسکتاپ وجود ندارد. شبکهٔ خود ناظر ممکن است مشکل داشته باشد؛ هشدار به معنی نیاز به بررسی است، نه اثبات قطعی سراسری سایت. با snapshot قدیمی‌تر از پنج دقیقه یا زمان آینده، گزارش stale است. clock و endpointهای عمومی جای صحت مالی و پایش همهٔ وابستگی‌ها را نمی‌گیرند.

## گزارش فارسی مستقل

بدون هیچ درخواست شبکه می‌توان آخرین snapshot را به JSON یا HTML فارسی تبدیل کرد:

```cmd
node scripts/record-site-health.mjs --state-file "%LOCALAPPDATA%\JamiMode-Monitoring\jamimode-health-history.json" --report
node scripts/record-site-health.mjs --state-file "%LOCALAPPDATA%\JamiMode-Monitoring\jamimode-health-history.json" --html > "%LOCALAPPDATA%\JamiMode-Monitoring\jamimode-health-report.html"
```

گزارش HTML فایل ثابت است؛ script، tracker، منبع بیرونی، refresh خودکار و form ندارد. وضعیت سه probe، تازگی نمونه، آخرین پاسخ‌ها و ده رویداد اخیر را نشان می‌دهد. با ثبت نمونهٔ تازه، برای نمایش جدید باید HTML دوباره ساخته شود. در PowerShell قدیمی برای redirect از Set-Content -Encoding utf8 استفاده کنید. stale بودن گزارش به معنای خرابی فعلی سایت نیست.

exit=0 برای نمونهٔ سلامت کامل/گزارش تازه است؛ exit=1 برای سلامت ناقص یا گزارش stale و exit=2 برای خطای ورودی/تاریخچه/ذخیره‌سازی. گزارش HTML با وجود stale بودن همچنان تولید می‌شود؛ در خطای ورودی خروجی JSON کلی است و باید exit code بررسی شود. ابزار --report/--html هیچ فایل را تغییر نمی‌دهد؛ نوشتن فایل گزارش فقط به‌دلیل redirect صریح اپراتور انجام می‌شود.

مرز تکمیل این بسته: ثبت امن API، محافظ رندر، probe یک‌باره، خلاصهٔ لاگ، snapshot محدود، تشخیص محلی اختلال/بازیابی و گزارش فارسی آماده و محلی آزموده‌اند. برای بهره‌برداری واقعی هنوز محل اجرای مستقل، زمان‌بندی مورد تأیید، مقصد/کانال اعلان، نگهداری لاگ سرور و پذیرش زنده باید تعیین/تأیید شوند. این موارد به درخواست قبلی مالک دربارهٔ موکول‌کردن تنظیمات هاست وابسته‌اند؛ تکمیل کد محلی به معنی نصب آن‌ها یا تکمیل همهٔ فاز۶ نیست.
