## Final behavior

The inventory row action opens capability checking, a signed integer delta form, a 3–500-character reason, a frozen before/delta/after preview and a separate confirmation. It adjusts the registered variant quantity by a stated increment/decrement; it is not an absolute physical stock count or an available/reserved quantity redesign. The expected quantity, SKU, size and color are frozen. A changed snapshot is rejected and requires closing/reopening after refreshing, preventing the old dialog from silently rebasing an operator's decision. Product and variant identity must match.

Each command carries one UUID idempotency key. A pending command is persisted before POST, per configured project/owner/product/variant, and held under an origin-shared Web Lock while dispatching. A conflicting pending command cannot overwrite it; absent lock support, unavailable/corrupt storage or failed persistence prevents dispatch. Ambiguous HTTP outcomes preserve the complete immutable command. Reopening/reloading uses the same key and payload; it cannot create a new correction by changing the reason or amount. Only a matching confirmed receipt clears it. An explicit database stale-snapshot rejection closes the unapplied exact request; role/server-gate failures retain it because they do not prove that a previous attempt never committed. Failed local cleanup after a confirmed receipt produces a warning, not a false failed mutation.

Pending records include operator reason and selection fields but no access token or file body. They are editable browser-local recovery data, never authorization or durable audit truth. Clearing browser data can lose them; they are not shared across devices/origins. Discovery currently occurs when opening the same variant; deleted/no-longer-visible variants and cross-device operational recovery need additional operator tooling. No automatic replay or unknown-request discard is added.

## Server and database boundaries

/api/admin/inventory/status, /adjustments and /history are mounted behind existing security headers, the bounded process-local rate limiter and the 32 KiB body parser. Supabase Auth getUser validates the bearer token; a database has_role lookup requires an explicit true admin result. User metadata and caller actor/user/after/price/status overrides are ignored or rejected. The verified actor UUID is supplied only by Express. Request and result fields are allowlisted; a malformed or mismatched receipt remains unconfirmed. Unknown network/database outcomes are not retried automatically or exposed as raw diagnostics. Auth/role/RPC HTTP requests have bounded deadlines.

Public trusted_inventory_status, trusted_inventory_adjust and trusted_inventory_history are SECURITY INVOKER, service-role-only functions with empty search paths. They recheck the current actor in public.user_roles; there is no new SECURITY DEFINER or browser-granted privileged routine. The private schema, RLS-enabled settings/history tables and routine permissions are explicitly restricted, including inherited-access checks for anon/authenticated. The service role can SELECT settings and SELECT/INSERT history, not UPDATE/DELETE/TRUNCATE history or enable the gate. SQL reason/delta/snapshot validation is independent of the UI/API.

The adjustment serializes actor/key replay, then locks parent product and variant in the same order as checkout and reservation expiry. It compares the exact captured stock/identity fields, updates quantity and inserts actor/key/reason/before/delta/after plus identity snapshots in one transaction. If the history insert fails, the stock update rolls back. Replaying the same key/body returns the original receipt even if stock subsequently changed; another body conflicts. Existing receipts can be returned after the database new-write gate closes, while actor authorization is still required. Quantity is bounded to a nonnegative PostgreSQL int32 and delta to +/-1,000,000. History has no cascading foreign keys and survives catalog/account deletion. UPDATE/DELETE trigger protection supplements restricted grants. A trusted database owner/service credential is outside the untrusted-browser threat model.

History reads use a bounded timestamp/UUID keyset cursor, preserving the six-digit timestamp string. The UI shows actor UUID, reason and before/after values and can request older entries. It explicitly covers only manual adjustments recorded by this new path, not reservation/settlement, historical edits or every stock movement. The legacy ProductVariantsManager stock writer remains unchanged and can bypass this new manual history. Value comparison is not a global catalog revision or a full warehouse ledger. Legacy writer lock order can still cause transaction aborts; no deadlock-free claim is made for all catalog writers.
