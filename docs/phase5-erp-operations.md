# Phase 5 ERP operations — prepared locally, not released

This continuation covers the other four Phase 5 task areas in the Notion roadmap. `/admin/erp` is protected by RequireAdmin and offers separate order/return/ticket operations, bounded customer/address/message views, paid-sales/cost reporting, activity records and page-scoped CSV. It is not a claim that the entire phase has passed hosted acceptance.

## Workflows and financial boundaries

The server supplies the session-verified actor, requires an explicit admin role and calls service-only invoker RPCs. SQL repeats role authorization. Operations require a reason, preview and separate confirmation; immutable actor/request-key receipts permit exact replay and reject different-payload reuse. Parent row locks and expected states/revisions reject competing/stale operations. Neither client status values nor a refund request establish payment.

- Fulfillment currently supports paid-v2 confirmed → processing → shipped (tracking reference required) → delivered. Paid confirmed/processing orders may also be cancelled through a reasoned operation. Cancellation does not refund money or restock goods. Reversing delivery or fabricating payment is prohibited.
- Return requests support pending → approved/rejected → received → closed as applicable, with a separate case revision. The order must be paid v2 and belong to the return applicant; approval requires shipped/delivered fulfillment. This does not automatically restock goods or refund money.
- Refunds are a single administrative case per paid order, capped at that order’s total: requested → approved/rejected; approved → externally_recorded requires an operator-entered evidence reference. Amount changes and second cases are not supported. Externally recorded is a manual claim, **not bank/provider confirmation**. Payment state, wallet, stock and provider remain unchanged. Automated/partial multiple-refund execution is unimplemented and must not be inferred.
- Pending or legacy-payment orders cannot be converted into paid orders through this console; they require existing reconciliation paths.
- Ticket status uses expected pending/resolved transitions. Existing messaging/composition screens remain; no real message was sent in development/testing.

The application gate `JAMI_ERP_ENABLED` defaults false. Database `erp_private.settings.operations_enabled` defaults false. Enabling that database gate closes direct browser UPDATE paths for orders, returns and tickets through a private trigger; the new service workflow must be available before activating it. Disabling the gate restores the previous browser behavior, not a financial rollback. Previously committed exact requests may replay while the DB gate is closed; an actor whose role was revoked cannot replay. A closed application gate prevents all ERP API service access.

## Customer/support reads

The resource allowlist is static; UUID cursors and parent IDs are bound parameters, and each page is at most 50 rows plus one for continuation. Address reads require one explicit customer UUID. Dynamic SQL selects only fixed templates, never user-controlled table/column names. API projections strip unrelated fields, including wallet balances/secrets from customer rows. Customer/address/ticket/message CSV buttons are deliberately unavailable. Ordinary resources use UUID ascending cursors. Activity/operations use descending (timestamp, UUID), with an optional exact actor/entity UUID filter. Invalid audit cursors reject. Each page is live, not a frozen global snapshot.

## Reports and purchase costs

Reports use an explicitly chosen UTC interval (exclusive end), maximum 366 days, applied to **order creation time** with current paid-v2 state. They show paid order count/total, included shipping, excluded legacy/unpaid count and up to 20 top product IDs by quantity. SQL numeric totals remain strings over HTTP; the browser does not sum money using floating-point arithmetic. Recorded manual refund evidence is separate and is not subtracted as verified bank cashflow.

Purchase unit costs can be recorded/corrected per paid order item, with reason, independent revision and immutable operation receipt. An explicit zero cost is valid; absent cost is unknown. Gross item margin is computed only when every paid order has items and every such item has a recorded cost. It equals sum((snapshot sale price − recorded unit cost) × quantity), may be negative, and excludes shipping, returns, tax and fees. It is **not net profit**. Existing historical costs are never invented or backfilled automatically.

CSV has UTF-8 BOM, quotes/escapes every cell and prefixes formula-leading cells to prevent spreadsheet formula execution. Record-list exports contain only the supplied current page and are labeled accordingly. Paid sales has a separate export of the complete aggregate for the selected range plus at most 20 top products, with unknown costs and manual evidence labeled explicitly; there is no all-record Excel workbook, frozen full export or download audit receipt yet.

## Activity and privacy

Private RLS activity/events tables are read-only to browser roles (in fact no private access), and only guarded API calls expose them to admins. The activity table has no service INSERT/UPDATE/DELETE/TRUNCATE grant. A narrowly scoped private SECURITY DEFINER trigger captures actual `auth.uid()` administrators on products, variants, orders, returns, tickets, messages, profiles and addresses. It binds the enum signature `public.has_role(uuid, public.app_role)` explicitly; a hostile text overload is tested.

The trigger records entity, actor, time, operation and changed field names. Before/after values are restricted to price, stock, sale flags, order/payment status, totals/shipping and read status; phone, address, message body and other profile values are omitted. Failure to append activity rolls back the originating admin mutation. Service routines without an actual admin JWT are not mislabeled as a browser manager: new ERP actions have their own actor-bound receipts; inventory retains its existing dedicated histories. This is not an audit of every possible owner/console/system operation. Trusted database-owner powers remain outside the append-only guarantee.

## Verification

The final checkpoint uses the associated work-output reports, not this document’s prose as test evidence. The full suite passed 1,421 tests in 86 files before the final CSV addition; the final affected suite passed 35 tests; 63 offline browser scenarios passed. ERP was tested on genuine disposable PostgreSQL both with the incremental containment harness and a fresh 42-migration synthetic bootstrap. The final fresh local bootstrap passed 77 ERP assertions and one real admin race. Final ERP assertions include an admin race, role-overload resistance, activity rollback, manual-refund boundaries, cost CAS, missing-cost refusal and positive/negative gross margin. Typecheck/lint/build/bootstrap checks pass. All fixtures are local/synthetic, and their clusters are stopped/removed; the isolated browser build must not be deployed.

Known acceptance gaps: full-record export/export-receipt support; broader legacy-image cleanup/history; actual-volume query latency; real Supabase Auth/PostgREST/RLS and coordinated publication. Existing per-product inventory child caps and global SKU mapping decisions remain documented in the inventory task. None of these are silently marked Done. After separate explicit approval, the ten Phase 5 migrations were installed only on jamimode-test/cifhcrlmjnsxpkhyloen. 53 hosted SQL-role/claims checks passed and all fixtures/gate changes rolled back. Both final counts (6 products, 2 variants, 0 orders) and zero histories/gates were read back. One actual anonymous PostgREST ERP request returned 401/42501; the inventory probe timed out. Actual GoTrue/password login and authenticated PostgREST acceptance have not passed. No production migration/activation, commit, push, merge, deployment, real payment/refund, SMS or email occurred.
