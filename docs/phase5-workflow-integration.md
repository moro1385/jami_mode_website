# Existing admin pages and the ERP workflow — 2026-10-25

Orders and tickets now mount the same reason/preview/confirmation dialog as the new ERP console. They no longer dispatch direct browser-table status writes from their controls. The return list opens the new returns section instead of offering its former unconstrained status dropdown. The ERP section query is allowlisted and only selects a view; it does not grant access or dispatch an operation.

The order-list read includes checkout_version and payment_state. Only a paid v2 order receives fulfillment controls; a legacy confirmed label alone is insufficient. Controls follow confirmed → processing → shipped → delivered, with the existing explicit cancellation branches. Shipment still requires a reference; fulfillment does not establish payment. Legacy or pending orders are read-only here and are not converted to v2 or paid. Refund cases remain in the ERP console and retain their separate manual-evidence boundary.

WorkflowActions is a presentation bridge, not another mutation implementation. The existing operation dialog preserves actor binding, request identity, reason, separate confirmation, response validation and uncertain-response retry. A disabled/unavailable API cannot fall back to the old browser write. Owner/entity keys remount the row action on account changes. Actions stop row-click propagation so that opening a workflow does not also open order details. Closing the operation rereads its list; an uncertain completion is never fabricated as success.

This closes the active UI paths only. Historical service/hook adapters remain for compatibility and their existing tests; deployed older clients are blocked only after the reviewed database workflow gate is enabled. The gated server and corresponding database migration must be available before publishing/activating these controls. With the ERP API closed, mutation remains unavailable by design. No new migration, gate change or hosted action occurred in this continuation.

Validation: typecheck, lint and isolated build pass. The complete unit suite and complete offline browser suite are recorded in the associated checkpoint. Targeted browser cases cover ticket read-denial/retry followed by the new persisted operation, order confirmation, disabled-server refusal without a table write, and routing from the old return list into the returns workflow. Unit tests retain unpaid/legacy containment and verify explicit confirmation, expected state, same-key uncertainty recovery, no old write and no false success. These are synthetic browser APIs, not actual Supabase Auth acceptance.
